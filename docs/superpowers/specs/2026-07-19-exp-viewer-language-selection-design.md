# 실험 뷰어 언어 선택 및 C++ 실행 설계

## 목표

참가자는 실험 세션 시작 전에 Python 또는 C++17을 한 번 선택한다. 선택한
언어는 세션 전체에서 고정되며, 언어별 과제 카탈로그·스타터 코드·실행 환경을
일관되게 사용한다.

## 사용자 흐름

1. 시작 화면에서 참가자 ID와 언어(Python/C++17)를 선택한다.
2. Python은 `exp_tasks.json`, C++17은 `exp_tasks_cpp.json`을 자동으로 불러온다.
3. 세션을 시작하면 언어 선택은 바꿀 수 없다. 모든 문제에 선택한 카탈로그의
   본문과 스타터 코드가 표시된다.
4. 실행 시 함수 인자 하나당 JSON 값 한 줄을 입력한다. 두 언어 모두 같은 입력
   순서와 JSON 표현을 사용한다.
5. 종료 결과의 각 과제 행에는 `language`가 기록된다.

## 클라이언트

- 언어 상태는 세션 상태로 보관하고, 카탈로그 URL 및 터미널 명령 표시는 이
  상태에서 파생한다.
- 기존 Python `execution_runner` 결합 방식은 유지한다.
- C++ 카탈로그의 각 과제에는 `execution_runner`를 추가한다. 이 래퍼는
  참가자 코드 뒤에 붙으며, JSON 줄 입력을 파싱해 `solution(...)`을 호출하고
  반환값을 출력한다.
- Python과 C++ 카탈로그의 과제 ID·세트·순서는 같아야 한다.

## 서버

- `POST /run` 요청에 `language` 필드를 추가한다. 생략 시 기존 호환성을 위해
  Python으로 처리한다.
- Python은 기존 인터프리터 실행을 유지한다.
- C++17은 임시 `.cpp` 파일을 `g++ -std=c++17 -O2`로 컴파일하고, 성공한
  바이너리를 같은 표준입력으로 실행한다. 컴파일 오류와 실행 오류는 기존
  `{ok, out}` 응답 형식으로 반환한다.
- 요청 제한 시간은 컴파일과 실행을 합친 전체 예산으로 적용하며, 임시 소스와
  바이너리는 항상 정리한다.
- `/ping`은 지원 언어와 C++ 컴파일러 사용 가능 여부를 반환한다. 클라이언트는
  C++ 선택 시 서버가 지원하지 않으면 실행 불가 원인을 명확히 표시한다.

## 배포와 검증

- Railway용 `Dockerfile`은 Python 런타임과 `g++`를 설치하고 기존
  `python run_viewer.py` 명령을 실행한다.
- Python 회귀 동작을 유지한다.
- C++ 컴파일·실행은 로컬 컴파일러가 있을 때 실제 검증하고, 없을 때는 해당
  검증을 건너뛴다. Docker/Railway 이미지에서는 실제로 검증 가능해야 한다.
- 테스트는 언어별 카탈로그 선택, C++ 실행 처리, 결과 언어 기록, 카탈로그
  동등성(과제 ID·세트)을 다룬다.

## 범위 제외

- 세션 중 언어 변경
- 사용자별 추가 컴파일 옵션 또는 외부 라이브러리 설치
- Python/C++ 외 언어 지원
